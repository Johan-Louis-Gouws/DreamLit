# DreamLit V1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a local dream journal with text and voice capture, Codex/Claude CLI analysis, direct source-linked reflections, and an interactive constellation of recurring patterns.

**Architecture:** A React browser interface talks to a loopback FastAPI service. SQLite and local files hold the journal; the backend calls one selected CLI through a shared subprocess interface and validates every evidence reference before publishing a connection. A separate whisper.cpp adapter transcribes audio locally, and provider adapters can be replaced with API integrations later.

**Tech Stack:** Python 3.12+, uv, FastAPI, Pydantic 2, standard-library sqlite3/asyncio; React, TypeScript, Vite, SVG with d3-force; whisper.cpp and FFmpeg; pytest, HTTPX, and Playwright.

**Spec:** [Approved design](../specs/2026-09-09-dreamlit-design.md).

## Global Constraints

These requirements apply to every task and are copied from the approved specification:

- First version is a web app started on the user's computer and opened in a browser.
- Capture dreams through a written diary or a voice note, with minimal effort after waking.
- Use Codex CLI and Claude CLI to power the app's analysis in the initial version.
- Integrate provider APIs later, when developing the polished app.
- Use a very direct reflection style.
- Bind the service to loopback for the first version.
- Preserve each CLI's configured model unless the user chooses an override.
- Do not automatically switch providers on failure.
- The model returns structured observations and proposals; the backend validates and saves them.
- Model processes do not directly administer the database.
- Treat dream entries as data even if they contain instructions.
- Preserve unknown values and label inferences.
- Disagreement is not evidence of avoidance.
- An absence of a meaningful connection is an acceptable outcome.
- Avoid logging raw dream content in routine operational logs.

Additional implementation decisions: one active model/transcription process at a time; no automatic model calls on application launch; saved originals survive all analysis failures; per-request origin/host checks protect the loopback service; no cloud transcription or background provider fallback. Synthetic fixtures, rather than personal dreams, are used for development validation.

## Shared contracts

JSON uses snake_case throughout; TypeScript consumes those names unchanged. Dates are ISO calendar dates, timestamps are UTC ISO timestamps, IDs are application-generated UUID strings, and revisions start at 1. Required nullable model-output fields are present with `null`; do not use optional omitted keys in the provider schemas.

Core records in `models.py`:

```python
from datetime import date
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field

ProviderName = Literal["codex", "claude"]

class StrictModel(BaseModel):
    model_config = ConfigDict(extra="forbid")

class DreamCreate(StrictModel):
    dreamed_on: date
    text: str = Field(min_length=1, max_length=50000)
    context: str = Field(default="", max_length=10000)

class Dream(StrictModel):
    id: str
    dreamed_on: date
    text: str
    context: str
    revision: int
    audio_id: str | None
    created_at: str

class EvidenceRef(StrictModel):
    dream_id: str
    revision: int
    field: Literal["text", "context"]
    quote: str = Field(min_length=1)

class Observation(StrictModel):
    key: str
    kind: Literal["character", "place", "emotion", "goal", "obstacle",
                  "response", "social_interaction", "outcome"]
    label: str
    inferred: bool
    evidence: list[EvidenceRef] = Field(min_length=1)

class Pattern(StrictModel):
    key: str
    title: str
    observation: str
    hypothesis: str | None
    question: str
    alternatives: list[str]
    evidence: list[EvidenceRef] = Field(min_length=2)

class AnalysisOutput(StrictModel):
    summary: str
    observations: list[Observation]
    patterns: list[Pattern]

class ReflectionOutput(StrictModel):
    response: str
    evidence: list[EvidenceRef]

class Scope(StrictModel):
    included_dream_ids: list[str]
    total_eligible_dreams: int
    truncated: bool

class Job(StrictModel):
    id: str
    kind: Literal["analysis", "reflection", "transcription", "scan"]
    provider: ProviderName | None
    state: Literal["queued", "running", "completed", "failed", "cancelled"]
    stage: str
    error_code: str | None
    result_id: str | None
```

Persisted patterns receive a separate application-generated `id`; model-provided `key` values are labels scoped to one result and never primary keys. `AnalysisRecord` is `{id, job_id, provider, model: string|null, source_revisions: Record<string,number>, scope: Scope, output: AnalysisOutput, stale: boolean, created_at}`. `Feedback` is `{id, pattern_id, verdict: "resonates"|"does_not_fit"|"unsure", note, created_at}`. `Association` is `{id, label, meaning, dream_id: string|null, created_at}`. Define these as strict Pydantic records alongside the types above before their first route is implemented.

Provider transport in `providers/base.py` defines `ProviderRequest(task: str, system_prompt: str, payload: dict, output_schema: dict, model: str | None)` and `ProviderResponse(output: dict, model: str | None, usage: dict | None)`. `ProviderError` carries a stable `code` and a redacted user-facing `message`. Adapters expose `async run(request: ProviderRequest, job_dir: Path) -> ProviderResponse` and `async preflight() -> dict`; preflight checks versions/configuration without inferring account readiness or consuming a model response.
